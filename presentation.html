Mini Compiler for
Arithmetic Expressions

A lightweight compiler for arithmetic expressions — covering lexical analysis, parsing, semantic checks, and code generation with evaluation.

Slide 2 • Background & Motivation

Introduction

Arithmetic expressions such as 3 + 4 * (2 - 1) are the classic starting point for studying how compilers work.

Evaluating an expression correctly means respecting operator precedence and parentheses — a compilation problem that uses the same phases as any programming language.

Why build a compiler for expressions?

  • Text must be tokenized, parsed & validated: Raw characters cannot be computed directly.
  • Errors must be caught before evaluation: Strict separation of compile-time and runtime.
  • A structured representation (AST) drives evaluation: Encodes syntactic hierarchy.
  • Precedence & parentheses need a formal grammar: Solved through recursive-descent parsing.
Slide 3 • Goals

Objectives

1. Tokenize Input

Design a lexical analyzer that converts the expression text into a clean stream of typed tokens.

2. Parse & Validate

Build a parser that checks expressions against a formal grammar and builds an AST.

3. Check Semantics

Verify operands, operators and divide-by-zero cases before evaluation.

4. Evaluate Result

Translate the AST into three-address code and evaluate it to a final value.

Slide 4 • Architecture

System Architecture

The compiler pipeline — from raw expression text to a computed result:

Source Input (3 + 4 * 2) → Lexical Analyzer (Tokens) → Parser (AST)
→ Semantic Analyzer (Validated AST) → Intermediate Code Gen (TAC) → Executor (Result Value)

Each stage passes a validated, richer representation of the expression to the next — mirroring a general-purpose compiler's front end and back end.

Slide 5 • Phase 1

Phase 1 — Lexical Analysis

  • Scans the raw expression string character by character.
  • Recognizes integer and decimal numbers.
  • Identifies operators (+, -, *, /, ^) and parentheses.
  • Strips whitespace between tokens.
  • Reports illegal characters as lexical errors.
Example — Tokenized Output: 3 + 4 * (2 - 1)
3 : NUMBER + : PLUS 4 : NUMBER * : MULTIPLY ( : LPAREN 2 : NUMBER - : MINUS 1 : NUMBER ) : RPAREN
Slide 6 • Phase 2

Phase 2 — Syntax Analysis (Parsing)

  • Consumes the token stream from the lexer.
  • Applies a context-free grammar for arithmetic expressions.
  • Uses recursive-descent parsing (expr → term → factor).
  • Builds a parse tree / Abstract Syntax Tree (AST).
  • Reports syntax errors with the offending token & position.
Resulting AST Structure:

The AST encodes precedence and parentheses: * binds tighter than +.

ADD_EXPR → LEFT(3) • OP(+) • RIGHT( 4 * (2 - 1) )
Slide 7 • Phase 3

Phase 3 — Semantic Analysis

  • Walks the AST to verify every node is well-formed.
  • Confirms every operator has the operands it needs.
  • Checks operand types (int vs. float) and promotes when mixed.
  • Detects division by zero in constant sub-expressions before runtime.
  • Produces a fully validated AST ready for code generation.
Example error caught:
"Semantic Error: division by zero in 8 / (4 - 4)"
Slide 8 • Phase 4

Phase 4 — Code Generation & Execution

  • The validated AST is translated into three-address code (TAC) with temporaries.
  • The executor evaluates this intermediate code instruction by instruction.
  • Respects precedence: * and / are generated before + and -.
  • Produces the final numeric result returned to the user.
Generated TAC:
t1 = 2 - 1
t2 = 4 * t1
t3 = 3 + t2
Result = 7
Slide 9 • Implementation

Tools & Technologies

1. Language

Python 3 & Modern ES6 JavaScript for implementing lexer, parser, analyzer & evaluator.

2. Parsing Approach

Hand-written recursive-descent parser over an arithmetic expression grammar.

3. Intermediate Form

Three-address code held as lists of quadruples [OP, ARG1, ARG2, RES] & temporaries.

4. Testing

Custom automated test suite of valid, edge-case, and malformed expressions.

Slide 10 • Validation

Testing & Results

  • Well-formed expressions with +, -, *, /, ^ and parentheses evaluate correctly.
  • Malformed expressions are rejected at the correct phase (lexical, syntax, or semantic).
  • Error messages identify the offending token and its exact column position.
  • Each phase's intermediate output (tokens, AST, TAC) can be inspected independently.
Sample test outcome:
Input: 3 + * 4;
Output: Syntax Error — unexpected token '*' near position 4
Slide 11 • Wrap Up

Conclusion & Future Scope

Conclusion

  • Successfully implemented all 4 core phases of a compiler for arithmetic expressions.
  • Reinforces lexical, syntax, and semantic analysis with AST-driven evaluation.
  • Produces correct results for valid expressions and clear diagnostics for invalid ones.

Future Scope

  • Support variables, assignments, and a persistent symbol table.
  • Add mathematical functions (sqrt, sin, abs).
  • Implement compiler optimizations such as constant folding.
  • Generate real assembly (x86 / ARM) or bytecode instead of interpreting TAC.
